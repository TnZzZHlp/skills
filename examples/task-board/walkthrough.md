# Grill Planner 流程示例

这是虚构演示，不是真实用户回答的记录。下面的产品需求、技术选择和确认均为模拟内容，尚未创建任何应用。

本示例按你的要求使用中文；技能本身及其默认输出语言仍保持此前确认的英文。

## 初始需求

**示例用户：** 我想做一个简单的任务看板，可以创建任务并跟踪进度。

## 第一轮：明确产品边界

**Agent：**

1. 这是一个人在一台电脑上使用，还是团队共同使用？如果协作不是必要需求，我建议先做本地单用户 MVP；团队共享会增加身份认证和权限控制。
2. 第一版必须支持哪些操作？我建议先包含创建、列表查看、修改状态和删除任务，暂不包含指派、评论和附件。
3. 关闭浏览器或重启应用后，哪些数据必须保留？我建议将任务持久化到本地数据库，而不是只保存在浏览器内存中。
4. 怎样证明第一版达到了目标？我建议以“创建任务、依次切换三个状态、重启应用、确认任务仍在正确列中”作为核心验收场景。

**示例用户：** 只在本地单人使用。这四个操作就够了，重启后数据必须保留。状态是待办、进行中和已完成。你提出的验收场景可以。

**Agent 小结：** 本地单用户任务管理属于本期范围；协作、登录和云部署不属于本期范围。因为需要重启后保留数据，纯前端内存原型无法满足目标。

## 第二轮：明确技术与交互决策

**Agent：**

1. 是否已有仓库或偏好的技术栈？针对这个新项目，我建议 React + Vite、Node.js/TypeScript API 和 SQLite。这样前后端使用同一语言，也不需要托管数据库。纯浏览器 IndexedDB 方案更简单，但不会提供独立 API。
2. 使用状态选择器是否足够，还是必须支持拖拽？我建议先使用选择器，实施成本更低，也便于键盘操作。
3. 任务标题是否允许为空或无限长？删除是否需要二次确认？我建议标题去除首尾空白后为 1–120 个 Unicode 码点，删除前要求确认，新任务默认进入“待办”。
4. 建议计划名为 `task-board`，输出到示例工作区下的 `docs/plans/task-board/`。服务仅监听本机回环地址，并拒绝跨来源的数据修改请求。是否接受？

**示例用户：** 使用这个技术栈和目录。选择器足够。接受标题规则、默认状态和删除确认。仅在本地运行。

## 统一核对

**Agent：**

- 目标：在一台电脑上，通过三列看板持续跟踪任务。
- 本期范围：创建、列表查看、修改状态、确认后删除。
- 非目标：身份认证、协作、云托管、拖拽、评论和附件。
- 架构：React 功能模块调用同源 API；任务服务负责业务规则；仓储模块负责 SQLite 操作。
- API：创建任务、获取列表、修改状态、按 ID 删除。
- 验收：浏览器操作流程可用，数据在重启后保留，写入失败不能显示为成功。
- 未提供性能数值，因此不自行编造性能指标。
- 本小型示例没有延期处理的非阻塞问题。
- 建议拆解：
  1. `001-task-api.md`：任务规则、持久化和 HTTP 契约。
  2. `002-task-board-ui.md`：浏览器交互，包括加载与错误状态。
  3. `003-end-to-end-validation.md`：跨层流程、重启与失败验证。
- 依赖关系：`001 -> 002 -> 003`。
- 将写入一个总计划和上述三个子计划。
- 请同时确认需求摘要与阶段拆解；确认只授权生成文档，不授权实施。

**示例用户：** 确认需求、计划名、输出路径和三个阶段的拆解，只生成计划。

## 实施期间的进度跟踪

根据本技能的进度约定，生成的任务与验收标准均使用 Markdown 复选框：

```markdown
- [ ] 002-T03：增加状态修改与删除确认
- [ ] 002-AC02：取消删除保留任务，确认删除移除任务
```

这不是已完成工作，示例不预先勾选。真实实施中，任务完成且所需检查通过后勾选对应任务；验收实际通过后勾选对应标准，并写明验证证据。

每个子计划全部任务与验收项完成后，同步子计划及总计划进度，并单独创建一次完成提交。例如阶段 002 完成后使用 `feat(task-board): complete subplan 002 - task-board-ui`，提交成功后再进入依赖阶段。不把多个子计划合并成一次提交，不暂存无关修改。

仅生成文档不算子计划实施完成，不执行提交；实施仍需单独授权。

## 建议检查的地方

- 追问是否足够深入，还是应该更简洁？
- 对于小项目，总计划是否过于详细？
- 实施任务是否具体到可以交给另一个 Agent 执行？
- 最终验证应该独立成一个阶段，还是合并到功能阶段？
